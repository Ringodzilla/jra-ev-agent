# JRA Race EV Analysis

JRA公式データを優先し、取得できた事実とモデル判断を分離して報告する。推測値で必須データを埋めない。

## 対象リポジトリ

通常は `jra-ev-agent` リポジトリで実行する。環境に示されたcwdが存在しない場合は、親ディレクトリ配下から同名ディレクトリを探索して実体を特定する。最初にリポジトリの `AGENTS.md` と `README.md` を読み、役割順序と最新CLIを優先する。

## 入力の解釈

- JRA URL、開催日、競馬場、レース番号、発走時刻を照合する。
- 「WIN5 5レース目」のような表記だけでWIN5モードにしない。1レースだけなら単レース分析として扱う。WIN5生成には対象5レースすべてが必要。
- 資金とモードの指定がなければ、リポジトリ既定の `1000円`、`balanced` を使い、採用した前提を報告する。

## ワークフロー

### 順序付き工程スキル

対象repoの `docs/skill_workflow.md` と `config/skill_workflow.json` を読み、`skills/jra-01-intake` から `jra-12-report` まで対応工程のSKILL.mdを順に適用する。購入申告は13、回顧は14を使用する。公開CLIの機械ゲートを有効なまま使用し、旧ライブラリAPIによる迂回は禁止。工程がBLOCKEDなら後工程を実施せず、未承認補完の対象と影響を示す。既存ユーザー承認は入力・用途・対象の一致を確認して引き継ぎ、自動承認はしない。機械検査をAIによる独立レビュー実施と説明しない。

### 計算前の欠損・補完監査

勝率・EV・買い目の新規計算または再計算前に、[jra-data-integrity-audit](../jra-data-integrity-audit/SKILL.md) を読み、項目別欠損と補完値のユーザー承認を確認する。履歴件数の充足だけで「欠損なし」としない。未承認・承認未確認の補完がある場合、収集と監査まで進め、補完を使う計算は確認が取れるまで停止する。下記の一括パイプラインは、監査未完了のまま分析まで実行しない。必要なら既存collectorだけを実行して監査入力を用意する。公式再取得・中立値の既定方針は、補完採用へのユーザー承認を意味しない。

1. 対象レース専用configの有無を確認する。なければ既存configの形式に合わせ、日付、競馬場、レース番号、URL、発走時刻、芝・ダート、距離、slug、title、tagsを持つ1件配列を作る。
2. `scripts/run_pipeline.py --force-rebuild` で、data collector → analyzer → simulator → EV calculator → bet builder → reviewer の順に事前分析する。取得済みrawだけを安全に再処理するときは `--reprocess-raw` を併用する。
3. 欠損を次の区分で監査する。
   - 必須・取得済み: 出走馬、馬番、枠、騎手、斤量、過去走件数、天候、馬場、全頭単勝、8券種の全組、取得時刻。
   - 必須・未取得: 馬体重・増減、欠けた過去走、欠けた券種または組番、天候・馬場、公式時刻。
   - 項目別に判定: 過去走の天候・オッズ・ペース・通過順も原典回収を行う。モデル未使用を取得省略や中立値補完の理由にしない。実測・未測定・未取得・未承認補完を分け、用途への影響を監査する。
   - データ欠損ではないもの: EV閾値未達、買い目0件、reviewerの定量NG。これらを「情報不足」と混同しない。
4. 当日かつT-5締切前なら `scripts/run_final_prediction.py` で最新スナップショットを再取得する。事前成果物の `pipeline_run.json` をbaselineに使う。
5. `final_decision.json` の `checks` を真偽ごとに確認する。取得で解消するfalseは対象と失敗経路を切り分けて再取得する。正常な別経路を試さず回数だけで打ち切らず、同じ失敗は無期限に繰り返さない。公式未発表、締切到達、JRA側欠落は推測で補完しない。
6. reviewerがNGなら正式な買い目を提示せず、NO_GOと具体的な理由を確定する。reviewerがOKでもticketsが空なら条件未達を示す。窓前の事前評価、締切に間に合わなかった未完了、評価済みの見送りを区別する。

## データ整合性

- 8券種は同じ `snapshot_id` であることを優先する。券種ページごとの取得時刻差を、同一スナップショットの不整合と誤判定しない。
- 旧形式で `snapshot_id` がない履歴を候補計算に渡す場合は、レースごとの最新 `captured_at` だけを現在オッズとして使う。過去時点はオッズ変動履歴にのみ使う。
- 確率合計は保存時の丸め誤差と実質的な不整合を区別する。修正する場合は正規化または既存の許容差方針に従い、恣意的に勝率を変えない。
- 再計算時間がオッズ鮮度上限を超えた場合は、全履歴を候補ごとに走査していないか確認する。現在オッズは最新スナップショット、変動評価は同一レース・同一券種・同一組番の履歴だけを渡し、再取得から判定まで鮮度内に収める。
- 対象レースの結果や確定払戻を予測入力へ混ぜない。

## 手動収集を依頼する条件

GET失敗やparserの空欄だけで公式データを取得不能と判断しない。過去走の欠損は、対象repoの `skills/jra-02-official-collection/SKILL.md` の回収手順に従い、公式結果と実在するオッズリンクのPOSTフォームまで確認する。通常の公式閲覧・再取得は依頼の範囲内で進め、補完承認を先に求めない。回収できたら新しい入力で監査を更新し、解消済みの欠損による停止を引き継がない。

自動再取得後も公式ページから得られない必須項目だけを依頼する。馬体重が単に未発表なら、手入力ではなく発表を待って再取得するよう案内する。過去走が不足し `report/missing_history_requests.json` にrequestsがある場合だけ、`report/manual_history_template.csv` の該当馬を埋めて `data/manual/horse_history_overrides.csv` に追加するよう案内する。

## 最終報告

次を簡潔に示す。

- 収集済み件数と取得時刻
- 必須欠損、任意欠損、取得を試みた結果
- reviewer判定と正式買い目の有無
- 次回再取得に適した時刻。通常は馬体重発表後かつT-5に間に合う時刻
- `note.md`、`pipeline_run.json`、`latest_decision.json`、必要なら手動入力テンプレートへのリンク

## 分析と判断の目的

- 人気・市場オッズから独立して馬同士の強弱と条件差を評価し、その確率とオッズの差から投資判断を行う。高オッズ・低人気・着順のばらつきだけで高EV候補を足切りしない。
- 勝率の平坦さ、スコア尺度、入力が特徴量へ接続されているかを確認する。高EVが単に高オッズ由来なら説明し、勝率推定の改善として扱う。診断を新たな購入拒否の閾値にしない。
- 機械PASSやテスト件数を精度の実績にしない。予算・鮮度・締切・補完承認の既存条件で買う／見送るを確定し、未検証の「安全性」条件を独自追加しない。
- 作業が継続している場合は直前更新と正式判断まで進める。後で自動更新すると言うのは実際に待機・実行が稼働している場合だけとし、窓前の事前評価を最終判断完了として終えない。
- レビューの役割は具体的な評価根拠・展開・確率・価格差の妥当性を判断すること。取得済み証拠や機械検査の重複作業で判断時刻を消費しない。
