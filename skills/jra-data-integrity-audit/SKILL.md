# 競馬データ欠損・補完監査

対象は通常 `/Users/konishi/Documents/Playground/projects/jra-ev-agent`。現在のAGENTS.md・README.mdを読み、対象race_id、入力スナップショット、対象馬、計算目的を確定する。これはデータ来歴の監査であり、能力評価・勝率計算・買い目生成は担当しない。

## 完了条件

次の3軸を独立して確認する。

- 件数：各馬について `min(5, 確認済み通算出走数)` 件の履歴があるか。未経験の走数を欠損と数えず、通算出走数不明は未確認とする。
- 項目：実際の履歴行・出馬表・環境・オッズに何が欠けているか。
- 来歴と承認：値が原典の観測・決定的変換・補完のどれか、補完をユーザーが明示的に承認したか。

「履歴取得漏れ0」と「項目欠損0」と「未承認補完0」は別の主張。件数・quality_report・reviewer OKだけから「欠損なし」と言わない。確認できない領域は未確認として残す。

## 調べ方

1. 入力のパス、取得時刻、SHA256、race_idを記録する。結果取得後の監査では発走前スナップショットだけを予測入力として扱う。
2. raw原典 → parser/正規化後の履歴 → analyzer特徴量 → simulator → EVの順に、実際に使われた入力を追跡する。監査用に必要な読み取りは行うが予測を再実行しない。
3. 各馬・各走の項目別表を作る。最低限、日付、競馬場、芝ダート、距離、着順、時計、斤量、騎手、上がり、通過順、ペース、天候、馬場、過去オッズ・人気を確認する。当日は出走馬・枠馬番・騎手・斤量、馬体重増減、天候馬場、環境測定値と測定時刻、8券種の全組番・公式時刻も確認する。非該当は理由を付けて欠損と区別する。
4. `rg`で実行経路上の `fallback`、`neutral`、`fillna`、`get(..., default)`、空欄処理、0/0.5の既定値、例外時の既定値を探索する。解析コードの存在だけでは採用と判定せず、対象行がその分岐を通った証拠と出力値を照合する。
5. 補完前に数値化された値も調べる。例：上がり未取得が36秒へ置換され、後段では非空になっている場合。値が0.5だから補完、非空だから実測とは判定しない。
6. 通過順欠損 → front_rate=0.5など、派生特徴量への影響を列挙する。一部履歴のみ利用・欠損行除外・利用可能な走への重み再配分・推定オッズへの代替も記録する。レース共通値を別日や別馬から流用していないか確認する。
7. 既存の承認を会話または証拠付き承認記録で確認する。補完対象・方法・用途・範囲が一致する明示承認だけを有効とする。コードの既定値、AGENTSの中立値方針、分析依頼、購入報告、沈黙は補完承認ではない。「未昇格モデルで試算」の承認も、別の履歴欠損補完の承認には拡張しない。証拠が見つからなければ `UNVERIFIED` とし、承認済みにしない。

## ユーザー確認が必要な場合

欠損はまず公式原典からの回収を試す。GET失敗・エラー013・parser未対応を原典の欠落と混同しない。収集担当へ対象repoの `skills/jra-02-official-collection/SKILL.md` に従う回収（公式結果内の実在オッズリンクとPOSTフォームの確認を含む）を依頼し、通常の原典取得で回収できる項目を補完承認へ回さない。回収不能なら試行したmethod・URL・送信パラメータ・応答と理由を残す。回収後は新しい入力SHA256に対して再監査し、過去のBLOCKEDや補完件数を現状へ転用しない。

- 未承認または承認未確認の補完を使った新規勝率・EV・買い目計算は停止する。研究試算も同じ。
- データを中立値へ置換してから確認しない。既に使われていた場合は、その計算結果を「未承認補完を含む参考値」と明示し、正式な根拠として使わない。
- 質問前に監査を完了し、馬・走・原項目・欠損数・採用予定値・補完方法・下流特徴量・影響が未定量かを具体的に提示する。原典再取得など独立して可能な監査は継続する。
- 「補完せず計算保留」または「列挙した補完だけ、このレースのこの用途に承認」を選べる形で尋ねる。返答を待つ。時間経過で承認を推定しない。
- 欠損を無視する、対象馬を除外する、閾値を緩めることで確認を迂回しない。
- 昇格モデルなしのenvironment_score=0は、観測欠損補完と区別した「環境補正未適用」として表示する。雨が織り込まれた勝率とは説明しない。

確認を求める際は、このSKILL.mdへのリンクと「未承認または承認未確認の補完を使った新規勝率・EV・買い目計算は停止する」を示す。既に範囲の一致する明示承認があれば再確認しない。

## 監査成果物

予測入力を変更せず、対象レース配下の新しい監査JSONに保存する。最低限：

- `race_id`, `input_artifacts`（path・SHA256・取得時刻）, `audit_scope`
- `history_counts`（馬別の通算・必要・取得・不足件数）
- `field_missingness`（馬・走・項目・欠損/非該当/未確認・原典）
- `imputations`（原欠損、採用値、方法、コード位置、実行証拠、下流用途）
- `approval_checks`（対象補完、APPROVED/NOT_APPROVED/UNVERIFIED、ユーザー発言の証拠と適用範囲）
- `gate`: `PASS` / `BLOCKED_UNAPPROVED_IMPUTATION` / `BLOCKED_MISSING_DATA` / `UNVERIFIED`
- `limitations`, `next_action`

`PASS`は指定用途の検査を完了し、必須欠損がなく、使用する全補完に有効な承認がある場合だけ。任意項目欠損がある場合も件数と用途への影響を残す。PASSはモデル精度や購入推奨を意味しない。影響を調べていない欠損を「非阻害」と呼ばない。

回答はJSONで、件数充足・項目欠損・補完採用・承認状況・停止理由を個別表示する。0件という集約だけで終わらせず、対象馬の重要項目を示す。

## 動作確認例

- 履歴22/22件でも、対象馬5/5走の通過順欠損とfront_rate=0.5の補完があれば、件数充足と補完停止を同時に報告する。
- 原典に実測0.5がある場合は、数値一致だけで補完と断定しない。
- 原典空欄・出力36秒・fallback証拠がある場合は、非空でも補完と判定する。
- 「100円買った」は過去の補完の承認にしない。
- 雨の係数0と通過順欠損による0.5を区別し、前者のモデル制約も隠さない。

## 予測目的に沿った監査

- この監査は事実・来歴・補完承認を確かめる。モデルの識別力や校正の評価は担当工程へ渡し、監査PASSを予測精度の証明にしない。
- 高オッズ、低人気、着順のばらつき自体を欠損・補完・停止理由にしない。未検証の保守的な足切りを追加しない。
- 未使用でも取得可能なペース・環境・通過順を回収する。実測していない項目と、未収集・未接続を分ける。取得済み値を捨てて中立値に置き換えない。
- 入力・コード・承認範囲が変わらない検査証拠は活用し、具体的な未確認箇所を解決する。監査の反復回数を成果にせず、同じ不足は収集担当へ対象と原典を示して戻す。
